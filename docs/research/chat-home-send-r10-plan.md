# R10：普通 ChatGPT 消息消费者

## 首要决策与待证项

沿用[全软件总计划](../FULL-REPLICA-PLAN.md)，不减少14批范围。固定官方26.1111.2228.0的首页非Work模型走ChatGPT会话准备和流式接口；不得交给普通CLI sender。此判断置信度高，来源为`chat-home-send-next-anchors.json`的实际调用链；详细请求、流schema和原生认证能力仍须补证，能改变实现的证据是相同版本的实际请求producer和事件消费者。

流运输与业务事件分开：Rust以现有系统curl/服务认证为基础增量读取，不把完整响应当逐字流；前端消费真实事件，不用定时器产生助手文本。此决定置信度高，若固定来源证明使用的服务只支持另一种必要通道，则继续实现对应通道并记录，不假SSE或假恢复。`sentinel`/attestation、上传、WS topic重连及消息存在性核验是待证输入，不能填假值或静默删除来让测试通过。

本阶段成功条件是可审阅的真实发送、响应、取消和恢复主链及相应原生候选，不能以单独parser或被禁用的发送按钮代替。没有真实账号/模型运行授权的测试仅使用自有隔离服务fixture；真实服务与像素仍明确未验。

## 假设

- 用户已授权按总计划持续开发及阶段本地提交，CI/push暂停；置信度高，来自当前用户指令。
- 现有身份、取消注册、service profile和DesktopStateManager继续复用；置信度高，已查当前源码`chatgpt_service.rs`、`chatgptService.ts`。
- 当前完整HTTP transport没有普通Chat流消费者；置信度高，当前源码检索与调用点核对。不能由此推断服务器会接受缺失的认证/完整性材料。
- 官方JS仅作只读取证，不整包复用或执行。行业惯例不作为业务事件或私有请求字段的来源。

## 语义清单与偏离规则

| 官方/标准行为 | 处理 | 原因与证明 |
|---|---|---|
| 首页非Work进入ChatGPT发送 | 保留 | 实际producer→typed请求→真实流消费者，回归禁止CLI旁路 |
| prepare、submit、stop、resume分立 | 保留 | 取证每个请求的输入、身份及结果；取消连接不冒服务器停止成功 |
| SSE UTF-8、CR/LF、data/event/id语义 | 等价实现 | 使用WHATWG framing规则，覆盖任意字节边界与中文；业务JSON由固定源定义 |
| curl内部进程与Electron fetch不同 | 适配 | 不改变可观察流结果；检查实际增量、错误、超限、取消kill/wait与清理 |
| 上传、WS和特殊认证分支 | 保留为完整范围 | 缺输入先补源与消费者，不填占位成功、不自动降为另一类会话 |

用户已有明确持续执行授权，本合同不另设确认门槛。遇到缺证时继续只读取证及无依赖层；“保守”表示保留原数据/草稿、暴露未知结果、不自动重发可能已生效的模型请求，不能把永久禁用包装为终态。破坏迁移、外部发布或真实付费执行须有对应授权；当前不执行这些动作。

## 机械执行顺序

1. 补固定源请求/响应/身份/恢复合同，分别核resource hash/header与精确UTF-16切片。
2. 增量transport、typed发送/停止/恢复、真实事件归并与存储，按依赖顺序接入。
3. 首页Chat草稿→会话→后续消息复用现有可用渲染组件，未知事件保留诊断，不能丢文本冒成功。
4. 修复竞态与回归，冻结源码，完成相关自动检查和原生构建，阶段本地提交。

## 验证

用自有服务或进程fixture证明首事件在EOF之前交付；UTF-8逐字节、跨行/跨chunk、错误HTTP/MIME、取消、超限和退出均可重现。业务回放必须来自已登记源schema，不以当前实现反推预期。再执行同一操作序列验证首页发送、真实ID接续、重复点击/晚响应、停止、断线与未知结果保稿；真实服务、GUI/IME、宽窄官方配对像素及用户验收单列。

参考：[WHATWG SSE解释规则](https://html.spec.whatwg.org/multipage/server-sent-events.html#event-stream-interpretation)、[curl手册](https://curl.se/docs/manpage.html)。这些只说明运输协议，不能证明私有Chat API字段。
