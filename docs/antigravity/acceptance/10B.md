# 10B Scheduled 真实执行终态与在途互斥

日期：2026-11-03。先完成[官方合同](../specs/10-run-completion.md)，再修改产品。
证据目录：`.ref/parity/10/actual/10B/`。

## 本轮改动

实际审查发现比历史持久化更优先的问题：原实现仅等待`thread/start`和`turn/start`
响应，就写completed并发完成通知。周期扫描也未阻止上一运行未结束时再次触发。

- 订阅先于turn/start；只处理匹配threadId与turnId的真实`turn/completed`。
  允许完成通知早于启动响应，无关thread/旧turn不能关闭当前运行。
- 手动启动响应返回running、真实thread/turn和startedAt；不再当执行完成。
  同一进程内的定时与手动启动共用持久running状态及同一状态互斥锁。
- 终态区分completed、failed、interrupted、unknown；未知/缺失状态不默认成功。
  断连、失去通知来源或重启遗留在途状态明确未确认，自动扫描不自动重跑unknown。
  用户仍可显式手动触发新运行；真实历史恢复和再次执行确认仍需后续对照。
- 保存运行声明失败时，不启动app-server执行；终态保存失败显示错误并保留内存结果，
  每5秒仅重试本地写盘，保存成功后才发布完成事件。保存重试不占住全局扫描循环。
  不再删除原状态文件以便强行rename。
- 终态使用真实完成观察时间lastFinishedAt；不再把lastRunAt启动时间当结束时间。
  UI按同任务startedAt身份合并通知和启动响应，早终态不被晚启动覆盖、重复终态不增加记录。
- App的toast、系统通知标题和旧本地通知档案分别显示完成、失败、中断或未知。
  沿用既有通知资格判断，不将本轮命名为完整官方通知策略实现。

复用现有Tauri事件、app-server桥、调度状态文件及页面事件归并，没有新增依赖。
监听通过`CompletionWatch`持有并在退出时解除；终态持久化重试前先释放监听。
Tauri事件API参见[官方Listener文档](https://docs.rs/tauri/latest/tauri/trait.Listener.html)。

## 回归与审查

- `running-before.log`：新增Rust回归先失败，确认running仍会再次调度。
- `frontend-before.log`：生产事件normalizer把interrupted改成completed，先失败。
- 前端专项执行生产normalizer、started/finished归并及既有操作callback；
  覆盖四种结果、缺失/不支持状态、早到/重复终态、旧结果不结束新运行。
- Rust专项覆盖匹配终态前持续pending、错误身份/未知状态过滤、早通知、失败/中断/断连、
  tick与manual交叉声明，以及隔离磁盘真实写入→覆盖→回读、写失败保留旧文件字节。
- 独立审查发现并修正：写失败仍启动任务的P1，以及失败任务的存储重试阻塞全局扫描的P2。
  最后只读复核无剩余阻断项；不把审查结论等同原生/服务运行通过。

## 原生验收步骤与未完成范围

在隔离CODEX_HOME及测试仓库运行对应源码构建：

1. 立即运行，确认启动回包后仍是运行中，没有提前出现完成通知。
2. 分别执行真实成功、失败、中断任务，核对对应thread/turn和页面、系统通知、存储读回。
3. 长任务跨过下次计划时刻并连续点击立即运行，只能有一个在途执行。
4. 断开app-server，明确结果未知；恢复后自动扫描不静默重复执行该任务。
5. 运行前制造状态文件不可写，确认不启动；运行结束时制造写失败，看到存储错误，
   恢复写权限后保存真实终态，不重复执行模型，其他任务不被保存重试阻塞。
6. 重开页面/应用，核对最近状态；逐次历史仍只是当前页面的最多20条记录，不能当持久run库。
